# Owner release acceptance

Current status for every row is **pending**. The Castvane UI row applies when the first-party UI is shipped or advertised. The backend acceptance rows apply to the first stable Core release. Use the exact candidate commit and record dates, environment, commands, failure diagnostics and final pass/fail in the release notes. Redact secrets and private media URLs.

| Gate | Prerequisites and procedure | Pass criteria and diagnostics |
| --- | --- | --- |
| Castvane UI | Pair the exact first-party UI build with the candidate Core. In a fresh browser profile, check discovery, bad and valid login, refresh, dashboard, stream creation and control, progress and reports, playback, storage, IAM, settings, and cluster administration on isolated services. | Supported workflows pass with expected permissions and error handling. Record both revisions, sanitized Network traces and console output. Keep [historical regression results](UI_REGRESSION.md) for reference. |
| NVIDIA | Supported proprietary driver and NVIDIA Container Toolkit when containerized. Pass GPU devices, run `nvidia-smi`, then `restreamer-core ffmpeg-check`. Encode and decode a generated stream with NVENC/NVDEC and repeat during concurrent jobs. | The device actually encodes and decodes. Compare worker inventory, utilization and reservation reporting to `nvidia-smi`. |
| Intel and AMD | Install matching kernel and VAAPI drivers. Grant the service access to the actual render node. Inspect `vainfo`, then run a local encode/decode with the intended QSV/VAAPI codec. | The physical device is in use and resulting media decodes correctly. GPU inventory and resource reporting reflect only measured capabilities. |
| Raspberry Pi | Use a supported 64-bit distribution, SoC-specific devices and a tested FFmpeg/FFprobe pair. Run diagnostics and one encode/decode with the actual supported acceleration path. | The physical hardware path is demonstrated and the app remains stable. Record OS, board revision, codecs and unavailable acceleration methods. |
| Multi-server cluster | Use at least three voters and separate worker(s) on real hosts with separate storage and private mTLS. Run writes and local media, restart one voter, isolate the leader, kill a worker, relocate and restore a member. Repeat with WAN-like latency and synchronized clocks. | Quorum rejects isolated writes. Ownership remains fenced, with measured interruption and restoration times. Use `/readyz`, `/api/v3/cluster`, `/api/v3/cluster/healthy` and authenticated node state. |
| 24-hour and 72-hour stability | Run the isolated recovery harness with `--seconds 86400` and `--seconds 259200`. Add long-running HLS/DASH, RTMP/SRT reconnects, storage rotation, ACME renewals and cluster stress on dedicated services. Capture concurrent viewer demand and varied failures. | No unexplained memory/FD/disk growth, leaked children or inconsistent state. Record timing, RSS and CPU from procfs, application metrics, request errors and disk usage. |
| Production-domain TLS | Use a controlled domain and a staging ACME directory first. Check challenge routing, renewal, certificate expiry alerts and RTMPS if enabled. Verify with `openssl s_client -verify_return_error`, `curl` and an FFmpeg RTMPS client. | Trusted hostname and chain, renewal survives restart, admin API gated, and media still works. Production issuance requires deliberate operator action. |
| Real S3 provider | Use disposable private AWS, R2 or provider test buckets. Run upload, multipart, range, list, cleanup, denied access, throttling and credential rotation. | No external production data changes. Confirm provider checksums, object metadata, lifecycle and permissions. |
| Representative migration | Take a read-only source copy. Use [migration commands](MIGRATION.md), verify inactive accounts, reset credentials, replay approved jobs, validate metadata and rehearse rollback. | No changes to source data, no legacy credentials activated and all approved workloads recovered. Review report and verify destination database integrity. |
| Distribution and final approval | Review attestations, matching source obligations, OS/architecture support, readiness report, security and manual evidence. Pull the registry image by digest and smoke-test both architectures. | Sign off the exact version and immutable artifact digests. Only then approve the first stable release. |

See [the automated status](PHASE_6_STATUS.md) and [UI results](UI_REGRESSION.md). Do not infer physical acceleration or deployment success from compiled capability lists.
